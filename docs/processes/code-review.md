# CraneApp — Pull Request и Code Review

Этот документ устанавливает единые правила оформления Pull Request и комментариев Code Review.

Основной процесс работы с задачами описан в [руководстве по работе с задачами](01-task-workflow.md).

---

# 1. Оформление Pull Request

При создании Pull Request GitHub автоматически добавляет шаблон из `.github/pull_request_template.md`.

Автор PR должен заполнить применимые разделы шаблона и удалить незаполненные служебные элементы. Один Pull Request должен соответствовать одной задаче или одной логически целостной подзадаче.

## What was done

Кратко описывает фактически выполненные изменения.

Раздел должен помогать ревьюеру быстро определить область изменения, но не должен полностью дублировать описание Issue.

Пример:

```markdown
## What was done

- Added `POST /api/v2/chats/{chatId}/members`.
- Added owner/admin permission checks.
- Added service and repository tests.
```

## Implementation notes

Содержит важные технические решения и детали, которые невозможно сразу понять из diff:

* архитектурные изменения;
* нетривиальные решения;
* известные ограничения;
* особенности транзакций;
* concurrency;
* изменения контрактов;
* migration impact;
* другие сведения, необходимые ревьюеру.

Для тривиальных изменений раздел может быть пустым или удалён.

Пример:

```markdown
## Implementation notes

Member creation and event publishing use the existing transaction/outbox
flow so that the event is not published if the transaction fails.
```

## How to test

Описывает последовательность проверки реализации:

* основной сценарий;
* важные негативные сценарии;
* ожидаемые результаты.

Инструкция должна быть достаточно конкретной, чтобы ревьюер или тестировщик мог воспроизвести проверку.

Пример:

```markdown
## How to test

1. Add an active user to a group as owner/admin.
2. Verify that the user appears in the member list.
3. Add the same user again and expect `409 already_member`.
4. Try the operation as a regular member and expect `403`.
```

## Related

Содержит ссылки на связанные GitHub Issue.

`Closes #123` связывает PR с реализуемой Issue и автоматически закрывает её после мержа в основную ветку.

`Parent: #110` указывает родительскую Feature, если PR реализует подзадачу.

Пример:

```text
Closes #123
Parent: #110
```

Если родительской Issue нет, строку `Parent` следует удалить. Номер Issue нельзя оставлять пустым.

# 2. Классификация комментариев Code Review

Каждый Review comment начинается с префикса, который определяет обязательность замечания.

## `blocking:`

Замечание обязательно должно быть устранено до merge.

```text
blocking: ошибка репозитория здесь игнорируется, поэтому API может вернуть
успешный response при неуспешной записи.
```

## `question:`

Требуется пояснение принятого решения или обсуждение. Сам вопрос не обязательно требует изменения кода.

```text
question: почему публикация события выполняется в отдельной goroutine?
```

## `suggestion:`

Рекомендуемое улучшение, которое само по себе не блокирует merge.

```text
suggestion: эту проверку можно перенести в service layer, чтобы handler
не содержал бизнес-логику.
```

## `nit:`

Незначительное замечание по читаемости, naming, formatting или аналогичным деталям. Не блокирует merge.

```text
nit: memberID будет точнее отражать назначение переменной, чем id.
```

# 3. Требования к Review comments

Review comment должен по возможности объяснять:

1. где находится проблема;
2. в чём заключается проблема;
3. почему она имеет значение.

Комментарий должен описывать техническую причину замечания и давать автору достаточно контекста для принятия решения.

Не следует использовать неконкретные комментарии:

```text
переделай
неправильно
исправь
зачем это?
тут можно лучше
```

Вместо этого необходимо объяснить проблему и её возможные последствия:

```text
blocking: проверка существования участника и INSERT выполняются отдельно.
При конкурентных запросах оба запроса могут пройти проверку. Необходимо
обеспечить корректность операции на уровне транзакции/БД.
```

Ревьюер не обязан всегда предлагать готовую реализацию. Если существует несколько корректных решений, разработчик может самостоятельно выбрать подход после понимания проблемы.

Автор PR должен отвечать на вопросы и сообщать об устранении обязательных замечаний. Если автор не согласен с комментарием, решение обсуждается в соответствующем Review thread.

Все обязательные замечания должны быть устранены или явно согласованы до merge.
