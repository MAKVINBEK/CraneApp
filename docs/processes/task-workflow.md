# CraneApp — руководство по работе с задачами

Этот документ описывает единые правила создания, планирования, выполнения и закрытия задач в CraneApp.

Цель процесса:

* задачи имеют единый формат;
* по идентификатору задачи понятно, к какой области она относится;
* крупные Feature разбиваются на независимые подзадачи;
* каждая задача связана с веткой и Pull Request;
* состояние разработки отражается в GitHub Project;
* в Sprint попадают только подготовленные и оцененные задачи;
* завершённые задачи соответствуют единому Definition of Done.

---

# 1. Идентификатор задачи

Каждая задача получает идентификатор:

`[MODULE-CATEGORY_NUMBER-SUBTASK]`

Базовый формат:

`MODULE-CATEGORYNNN`

Например:

`CHAT-F001`

Подзадача:

`MODULE-CATEGORYNNN-NN`

Например:

`CHAT-F001-04`

Полный заголовок Issue:

`[CHAT-F001-04] Исправить управление ролями участников группы`

---

# 2. Module

Module определяет функциональную или техническую область задачи.

Используем существующие модули проекта, например:

| Module  | Область                                          |
| ------- | ------------------------------------------------ |
| `AUTH`  | авторизация, аутентификация, токены, пароли      |
| `CHAT`  | чаты и управление чатами                         |
| `MSG`   | сообщения                                        |
| `USER`  | пользователи, профиль, настройки                 |
| `PAY`   | платежи                                          |
| `REPO`  | структура репозитория и техническое обслуживание |
| `SEC`   | безопасность                                     |
| `MEDIA` | файлы и медиа                                    |
| `CALL`  | звонки                                           |
| `INFRA` | инфраструктура                                   |

Новые Module-коды добавляются только тогда, когда появляется отдельная устойчивая область системы.

Не нужно создавать новый Module для одной задачи.

---

# 3. Category

Категория показывает характер работы.

| Код | Category      | Использование                                                  |
| --- | ------------- | -------------------------------------------------------------- |
| `B` | Bug           | исправление существующего неправильного поведения              |
| `F` | Feature       | новая функциональность или существенное изменение существующей |
| `T` | Test          | отдельная задача на тестирование                               |
| `L` | Legacy        | удаление или переработка legacy-кода                           |
| `D` | Documentation | документация                                                   |

Примеры:

`AUTH-B041` — bug в Auth.

`CHAT-F001` — feature для Chat.

`REPO-L001` — работа с legacy в репозитории.

`AUTH-T003` — отдельная задача на тестирование Auth.

`CHAT-D002` — задача по документации Chat.

---

# 4. Нумерация

Для каждой комбинации Module + Category используется последовательная нумерация:

`001`, `002`, `003` ... `041`.

Примеры:

`CHAT-F001`

`CHAT-F002`

`CHAT-B001`

`AUTH-F001`

Нумерация Feature и Bug независимая.

То есть одновременно могут существовать:

`CHAT-F001`

и

`CHAT-B001`.

Номер уже существующей задачи повторно не используется, даже если Issue был закрыт или задача отменена.

---

# 5. Подзадачи

Если задача достаточно большая, она создаётся как родительская Feature и разбивается на Sub-issues.

Пример:

`[CHAT-F001] Реализовать полноценное управление групповыми чатами`

Структура:

```text
CHAT-F001
├── CHAT-F001-01
├── CHAT-F001-02
├── CHAT-F001-03
├── CHAT-F001-04
└── CHAT-F001-05
```

Пример:

```text
[CHAT-F001] Реализовать полноценное управление групповыми чатами

├── [CHAT-F001-01] Реализовать редактирование данных группы
├── [CHAT-F001-02] Реализовать добавление участника
├── [CHAT-F001-03] Реализовать самостоятельный выход из группы
├── [CHAT-F001-04] Исправить управление ролями
└── [CHAT-F001-05] Интегрировать mute/unmute и ban/unban
```

Подзадачи связываются с родительской Issue через GitHub Sub-issues.

Родительская Feature используется для:

* описания общей цели;
* хранения общего контекста;
* объединения связанных изменений;
* контроля прогресса;
* итоговой интеграции Feature.

Непосредственная разработка ведётся преимущественно в подзадачах.

---

# 6. Заголовок Issue

Формат:

`[ID] Краткое описание результата`

Например:

`[REPO-L001-04] Удалить устаревший снапшот CraneApp-main`

или:

`[CHAT-F001-02] Реализовать добавление участника в групповой чат`

Заголовок должен описывать конкретный результат.

Плохо:

`[CHAT-F001-02] Чаты`

`[CHAT-F001-02] Исправления`

`[CHAT-F001-02] Backend`

Хорошо:

`[CHAT-F001-02] Реализовать добавление участника в групповой чат`

---

# 7. Описание задачи

Задача должна содержать достаточно информации, чтобы разработчик понимал ожидаемый результат без необходимости восстанавливать требования самостоятельно.

Рекомендуемая структура:

## Контекст

Почему требуется изменение и какую проблему оно решает.

## Требуется

Что необходимо реализовать.

## API / контракт

Если задача изменяет API:

* endpoint;
* method;
* request;
* response;
* error codes;
* WebSocket events;
* другие изменяемые контракты.

## Проверки и ограничения

Необходимые бизнес-правила и валидация.

## Критерии приёмки

Наблюдаемые условия, при выполнении которых задача считается реализованной.

Пример:

```text
## Требуется

- Добавить POST /api/v2/chats/{chatId}/members.
- Проверить существование пользователя.
- Проверить, что пользователь активен.
- Проверить, что пользователь ещё не состоит в группе.
- Проверить, что пользователь не заблокирован.
- Разрешить операцию owner и admin.
- Отправлять chat_member_added.

## Критерии приёмки

- Новый пользователь появляется в списке участников.
- Группа появляется в списке чатов добавленного пользователя.
- Повторное добавление возвращает 409 already_member.
- Заблокированный пользователь возвращает 409 user_banned.
- Несуществующий пользователь возвращает 404 user_not_found.
- Добавление пользователя в private chat невозможно.
- Изменение появляется у участников без ручного обновления страницы.
```

# 8. Definition of Ready

В Sprint разрешается брать только подготовленные задачи.

Задача считается `Ready`, если:

* понятна цель задачи;
* описан ожидаемый результат;
* определены критерии приёмки;
* известны основные ограничения и проверки;
* определён родительский Feature, если задача является подзадачей;
* назначен Priority;
* задача оценена в Story Points;
* нет неизвестной блокирующей зависимости;
* разработчик понимает, что именно необходимо реализовать.

Если требования требуют дополнительного исследования, задача остаётся в Product Backlog либо сначала создаётся Research-задача.

---

# 9. Поля GitHub Project

Для рабочих задач используются следующие поля.

## Status

Отражает текущее состояние выполнения задачи.

`Backlog` — задача существует, но ещё не подготовлена к работе.

`Ready` — задача подготовлена, попала в Sprint и может быть взята разработчиком.

`In Progress` — разработка начата.

`In Review` — создан Pull Request и проводится Code Review.

`Testing` — реализация проходит проверку.

`Blocked` — выполнение невозможно продолжить из-за блокирующей зависимости или проблемы.

`Done` — задача полностью завершена.

## Sprint

GitHub Iteration.

Определяет, в каком Sprint выполняется задача.

Задачи без Sprint находятся в Product Backlog.

## Priority

Используется:

`P0` — критическая задача.

`P1` — высокая важность.

`P2` — обычная задача.

`P3` — низкий приоритет.

## Story Points

Оценка относительной сложности задачи.

Используем:

`1, 2, 3, 5, 8, 13`.

Задачи больше `13 SP` необходимо рассмотреть на предмет дополнительного декомпозирования.

## Type

Например:

* Feature
* Bug
* Refactor
* Research
* Tech Debt
* Documentation

## Epic

Определяет крупное продуктовое направление.

## Component

Определяет техническую область реализации.

Например:

* Backend
* Frontend
* Gateway
* Crypto
* Infrastructure
* MLS

## Release

Версия продукта, в которую планируется включить изменение.

Например:

`v0.1.0`

`v0.2.0`

`v1.0.0`

Release не является Sprint.

Один Release может включать несколько Sprint.

---

# 10. Product Backlog

Все новые задачи первоначально находятся в Product Backlog.

Для них:

* Sprint не назначен;
* Priority может быть назначен сразу;
* требования могут уточняться;
* Story Points могут отсутствовать до refinement.

Наличие задачи в Product Backlog **не означает**, что команда обязуется её реализовать.

Перед Sprint Planning backlog должен быть приоритизирован.

---

# 11. Sprint Planning

Во время Sprint Planning команда выбирает задачи из Product Backlog.

Перед добавлением задачи в Sprint необходимо проверить Definition of Ready.

Для выбранной задачи:

1. Проверить требования.
2. Обсудить неизвестные.
3. Оценить Story Points.
4. Проверить зависимости.
5. Назначить Sprint.
6. Перевести Status в `Ready`.

После начала Sprint новые задачи в него обычно не добавляются.

Исключение — критические задачи, которые действительно требуют немедленной реакции.

Если такая задача добавляется, необходимо учитывать, что она изменяет первоначальный объём Sprint.

---

# 12. Работа с задачей

Разработчик выбирает задачу со статусом `Ready`.

Перед началом работы:

* назначает себя Assignee;
* переводит задачу в `In Progress`;
* создаёт рабочую ветку.

Разработчик не должен одновременно держать большое количество задач в `In Progress`.

Предпочтительный принцип:

> закончить текущую задачу прежде, чем начинать следующую.

---

# 13. Ветки

Для каждой непосредственно реализуемой задачи создаётся отдельная ветка.

## Feature

Для большой Feature:

`feature/CHAT-F001`

Она создаётся от `master`.

Для подзадач:

`feature/CHAT-F001-01-add-member`

`feature/CHAT-F001-02-remove-member`

Ветки подзадач создаются **от feature-ветки родительской задачи**, если Feature должна интегрироваться как единое изменение.

Структура:

```text
master
└── feature/CHAT-F001
    ├── feature/CHAT-F001-01-edit-group
    ├── feature/CHAT-F001-02-add-member
    ├── feature/CHAT-F001-03-leave-group
    └── feature/CHAT-F001-04-fix-roles
```

## Bug

Формат:

`bugfix/AUTH-B041-short-problem-description`

Например:

`bugfix/AUTH-B041-invalid-refresh-token`

## Legacy / refactoring

Рекомендуемый формат:

`refactor/REPO-L001-04-remove-old-snapshot`

## Documentation

`docs/CHAT-D002-update-group-api`

## Tests

`test/AUTH-T003-password-validator`

Название ветки должно содержать ID задачи.

Это позволяет по ветке, PR и commit history определить связанную Issue.

---

# 14. Работа с Feature-ветками

Если Feature состоит из нескольких связанных подзадач, создаётся интеграционная Feature-ветка.

Например:

`feature/CHAT-F001`

Она создаётся от актуального `master`.

Подзадача:

`feature/CHAT-F001-02-add-member`

создаётся от:

`feature/CHAT-F001`

После реализации подзадачи Pull Request открывается:

```text
feature/CHAT-F001-02-add-member
        ↓
feature/CHAT-F001
```

После Code Review и проверки PR мержится в Feature-ветку.

После завершения всех необходимых подзадач:

```text
feature/CHAT-F001
        ↓
master
```

создаётся итоговый Pull Request.

Feature считается интегрированной в продукт только после мержа итогового PR в `master`.

Feature-ветка должна регулярно синхронизироваться с `master`, особенно если живёт продолжительное время.

Не следует создавать долгоживущую Feature-ветку для набора независимых изменений. Независимые небольшие задачи предпочтительно мержить непосредственно в `master` через отдельные PR.

---

# 15. Pull Request

Один Pull Request должен соответствовать одной задаче или одной логически целостной подзадаче.

В названии PR указывается ID задачи.

Например:

`[CHAT-F001-02] Реализовать добавление участника в групповой чат`

PR должен быть связан с соответствующей GitHub Issue.

При открытии PR задача переводится:

`In Progress → In Review`

Во время Review проверяются:

* корректность реализации;
* архитектурное решение;
* соответствие требованиям;
* обработка ошибок;
* тесты;
* обратная совместимость;
* изменения контрактов;
* потенциальные race conditions / security / performance проблемы, если применимо.

Замечания Code Review исправляются в той же ветке.

---

# 16. Rework после Code Review

Отдельный статус `Rework` не используется.

Если во время Review найдены замечания, задача остаётся:

`In Review`.

Разработчик вносит исправления, после чего Reviewer повторно проверяет PR.

Если выяснилось, что требуется существенная переработка требований или архитектуры, задача может быть возвращена:

`In Review → In Progress`.

---

# 17. Testing

После успешного Code Review задача переводится:

`In Review → Testing`

На этом этапе проверяется не только наличие работающего кода, но и выполнение Acceptance Criteria.

Проверяются:

* основной сценарий;
* негативные сценарии;
* ошибки;
* права доступа;
* интеграция frontend/backend;
* WebSocket-события;
* изменения API;
* regression-sensitive сценарии.

Если найден дефект реализации текущей задачи, она возвращается в `In Progress`.

Если обнаружен отдельный независимый Bug, создаётся новая Issue категории `B`.

---

# 18. Blocked

`Blocked` используется только когда разработчик объективно не может продолжить работу.

Например:

* отсутствует необходимый API другой команды;
* задача зависит от незавершённой подзадачи;
* требуется решение по архитектуре;
* отсутствует доступ к инфраструктуре;
* внешний сервис недоступен.

При переводе в `Blocked` в Issue обязательно указывается:

* что блокирует работу;
* что необходимо для разблокировки;
* кто или какая задача является зависимостью.

`Blocked` не используется как статус «я пока этим не занимаюсь».

---

# 19. Definition of Done для подзадачи

Подзадача считается `Done`, если:

* реализация завершена;
* Acceptance Criteria выполнены;
* необходимые тесты написаны или обновлены;
* тесты проходят;
* PR прошёл Code Review;
* замечания Review исправлены;
* документация/OpenAPI обновлены, если менялся контракт;
* реализация прошла Testing;
* PR смержен в соответствующую Feature-ветку либо `master`.

Только после этого:

`Testing → Done`

---

# 20. Definition of Done для Feature

Родительская Feature имеет более строгий Definition of Done.

Feature считается `Done`, если:

* завершены все обязательные Sub-issues;
* интеграция подзадач проверена совместно;
* Feature выполняет общие Acceptance Criteria;
* regression tests проходят;
* API/документация актуальны;
* итоговый PR прошёл Code Review;
* Feature-ветка смержена в `master`.

То есть:

```text
CHAT-F001-01 ─ Done
CHAT-F001-02 ─ Done
CHAT-F001-03 ─ Done
CHAT-F001-04 ─ Done
        │
        ▼
feature/CHAT-F001
        │
     final PR
        │
        ▼
      master
        │
        ▼
CHAT-F001 ─ Done
```

`Done` подзадачи и `Done` Feature — не одно и то же.

---

# 21. Если задача не завершена за Sprint

Задача **не переводится в Done искусственно**.

В конце Sprint фиксируется её фактическое состояние.

На следующем Sprint Planning принимается решение:

* перенести задачу в следующий Sprint;
* вернуть в Product Backlog;
* изменить приоритет;
* декомпозировать;
* отменить.

Незавершённая задача не считается выполненной при расчёте Velocity.

---

# 22. Срочные задачи во время Sprint

Не каждая неожиданная задача является причиной менять Sprint.

Если появился Bug, сначала определяется его Priority.

`P0` может быть добавлен в текущий Sprint немедленно.

Для `P1-P3` по умолчанию создаётся Issue и задача попадает в Product Backlog для последующего планирования.

Добавление задачи в активный Sprint является изменением Sprint Scope и должно быть осознанным решением, а не обычным способом работы.

---

# 23. Жизненный цикл задачи

Полный стандартный путь:

```text
Создание Issue
      │
      ▼
Product Backlog
      │
      │ Refinement
      ▼
Definition of Ready
      │
      │ Sprint Planning
      ▼
Ready
      │
      │ разработчик начинает работу
      ▼
In Progress
      │
      │ Pull Request
      ▼
In Review
      │
      │ Review approved
      ▼
Testing
      │
      │ Acceptance Criteria выполнены
      ▼
Done
```

При блокировке:

```text
In Progress
     │
     ▼
  Blocked
     │
 проблема устранена
     ▼
In Progress
```

---

# 24. Пример полного цикла

Создаётся Feature:

`[CHAT-F001] Реализовать полноценное управление групповыми чатами`

Создаётся Sub-issue:

`[CHAT-F001-02] Реализовать добавление участника в групповой чат`

Во время Sprint Planning:

```text
Priority: P1
Story Points: 5
Sprint: Sprint 1
Release: v0.1.0
Status: Ready
Assignee: developer
```

Создаётся ветка:

`feature/CHAT-F001-02-add-member`

от:

`feature/CHAT-F001`

Разработчик начинает работу:

`Ready → In Progress`

Создаёт PR:

`[CHAT-F001-02] Реализовать добавление участника в групповой чат`

Target:

`feature/CHAT-F001`

Статус:

`In Progress → In Review`

После Review:

`In Review → Testing`

После успешной проверки и мержа:

`Testing → Done`

Когда завершены все `CHAT-F001-XX`, создаётся итоговый PR:

```text
feature/CHAT-F001
        ↓
master
```

После интеграционной проверки и мержа:

`CHAT-F001 → Done`

# 25. Основной принцип

GitHub Project должен отражать **реальное состояние разработки**.

Нельзя:

* оставлять начатую задачу в `Ready`;
* переводить незавершённую задачу в `Done`;
* держать заблокированную задачу в `In Progress` без комментария;
* создавать PR без связанной Issue;
* добавлять незапланированные задачи в Sprint без причины;
* использовать одну Issue для нескольких независимых изменений;
* использовать одну ветку для нескольких независимых задач.

Если состояние разработки изменилось — состояние задачи в Project также должно быть обновлено.
